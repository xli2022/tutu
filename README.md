# tutu

A little arcade of self-contained web apps, published to GitHub Pages.

**Live:** https://xli2022.github.io/tutu/

## Layout

The site is served straight from the repository root, so the site files *are*
the repo:

```
index.html                   # the hub: renders a card per app
.nojekyll                    # serve files as-is; do not run Jekyll
assets/
  site.css                   # shared design tokens (candy palette, buttons, backdrop)
  hub.css  hub.js            # hub-only styles + card rendering
  apps.js                    # THE APP REGISTRY
  fonts/fredoka-latin.woff2  # self-hosted; no third-party requests
  favicon.svg
apps/
  sugarsnap/                 # one folder per app
    index.html  sugarsnap.css  sugarsnap.js
  spendscape/
    index.html  spendscape.css  spendscape.js   # page, styles, state + wiring
    formats.js  categories.js  analysis.js      # parsing, categorising, numbers
    pdfstatement.js                             # reading PDF statements
    vault.js                                    # password-locked storage
    charts.js   sample.js                       # SVG charts, demo statements
    vendor/pdfjs/                               # Mozilla pdf.js, unmodified
  honglou/                   # 还泪记, a visual novel
    index.html  honglou.css  honglou.js         # page, styles, wiring + saves
    engine.js   story.js                        # script reader, the story itself
    stage.js                                    # scenes, figures, particles, transitions
    paint.js    scenery.js  buildings.js        # drawing kit, nature, architecture
    scenes.js   scenes-rooms.js                 # the eleven backdrops
    figures.js  cast.js                         # paper-cut figures, the roster
    audio.js                                    # procedural guzheng and sounds
    fonts/                                      # three subset OFL fonts + build.py
```

No build step and no external requests: plain static files. The third-party
pieces are Mozilla's [pdf.js](https://mozilla.github.io/pdf.js/), vendored
unmodified in `apps/spendscape/vendor/pdfjs/` (see its README for version and
checksums) and loaded only when someone opens a PDF, and three OFL fonts for
还泪记, subset and self-hosted in `apps/honglou/fonts/` with their licences. Everything
also works opened straight from disk, except reading PDFs: browsers don't load
JavaScript modules from `file://`, so that needs the page served over http(s).

## Adding an app

1. Create `apps/<slug>/` with its own `index.html`.
2. Link `../../assets/site.css` to inherit the shared look, and `../../` to get home.
3. Add one entry to `window.TUTU_APPS` in `assets/apps.js`:

```js
{
  slug: "my-app",              // must match the folder name
  name: "My App",
  tagline: "One short line",
  blurb: "A sentence or two for the card.",
  tags: ["Puzzle"],
  accent: ["#8fd4ff", "#1878d4"],   // card thumbnail gradient
  icon: "candy",               // a key of ICONS in assets/hub.js
  cta: "Open",                 // optional button label; defaults to "Play"
  status: "live",
}
```

The hub picks it up automatically. Everything in the repo is published, so
there is nothing else to wire up.

## Apps

### Sugarsnap

A triple-match candy puzzle. Tap any candy that is not covered and it flies into
the tray; three of a kind pop. Fill every tray slot and you are out. Ten levels,
ten candies, plus undo / shuffle / hint. Progress is kept in `localStorage`.

Boards are generated by **simulated solve**: the generator repeatedly takes three
currently-uncovered positions and stamps them with one candy type, so every board
is guaranteed clearable — a player who finds that order never needs more than
three tray slots. Types still land scattered across layers, so finding it remains
a real puzzle.

A tap plays out in beats: the candy flies to its tray slot (340ms) before the
match is allowed to resolve, the three matched candies then swell in place,
slide into the middle one and burst; candies uncovered by the tap light up a
beat later, once the candy that was covering them has moved off.

#### Difficulty

The ramp is measured, not guessed. The percentages below are how often a
competent solver that **never uses a power-up** clears each level, over hundreds
of simulated runs:

| # | Level | Tiles | Candies | Layers | Tray | Win |
|---|-------|------:|--------:|-------:|-----:|----:|
| 1 | Sweet Start | 21 | 4 | 2 | 7 | 100% |
| 2 | Jelly Garden | 30 | 5 | 2 | 7 | 100% |
| 3 | Gummy Grove | 45 | 6 | 3 | 7 | 100% |
| 4 | Lollipop Lane | 60 | 7 | 3 | 7 | 99% |
| 5 | Caramel Court | 81 | 8 | 4 | 7 | 99% |
| 6 | Marshmallow Mile | 87 | 9 | 4 | 7 | 83% |
| 7 | Toffee Tower | 102 | 10 | 4 | 7 | 76% |
| 8 | Liquorice Labyrinth | 120 | 10 | 5 | 7 | 67% |
| 9 | Peppermint Peak | 150 | 10 | 5 | **6** | 38% |
| 10 | Candy Castle | 165 | 10 | 6 | **6** | 25% |

Three levers, in order of strength:

- **Layer shape.** Levels 1–5 are pyramids, shrinking on both axes, so every
  layer keeps an exposed fringe and there is always plenty of choice. From 6 on
  the rows stay constant, which stacks each column in line: reaching the bottom
  of a column means peeling every layer above it in order. This is what actually
  makes the late levels hard — a pyramid sits near 95% however big it gets.
- **Tray size.** Taking one slot away is a far stronger squeeze than any amount
  of extra tiles, and it keeps the board legible, so the last two levels use it
  rather than stacking deeper. Depth stops at six layers: at seven the free
  tiles shrink to a narrow stripe and the board stops reading as a pile.
- **Candy count and power-up budget**, tapering from 4 candies and a full
  three-undo kit to all 10 candies with a single hint.

`window.Sugarsnap` exposes `state()`, `pick(id)`, `start(level)`, `undo()`,
`shuffle()`, `hint()` and `settle()` for driving the game from a test harness.
`settle()` resolves every in-flight placement at once, for tests that care
about board logic rather than animation timing.

### Spendscape

A bank statement explorer. Drop in the files your bank lets you download and it
sorts every transaction into a category and charts your spending over time:
stacked bars, a flowing stacked area or trend lines by category; money in
against money out; a day-by-day calendar; where the income went; top
merchants; bills and subscriptions it spotted; plain-language insights; and a
searchable transaction list where any transaction can be re-filed.
"Try it with sample data" loads fifteen months of made-up statements for two
accounts.

**Nothing leaves the browser.** Files are read with `FileReader` and parsed in
the page; there are no network requests. PDFs are opened by the vendored pdf.js
in a worker served from the same site, given the file's bytes directly, with
code evaluation and every fetch it could make (fonts, character maps,
WebAssembly, colour profiles) switched off; a locked PDF's password is used to
open it and is not kept.

**What is kept is locked with the user's password.** After the first import,
Spendscape offers to keep the statements in the browser (`localStorage`, entry
`tutu.spendscape.v1`) for next time, sealed with a password the user chooses;
the next visit opens on a lock screen that asks for it. `vault.js` seals with
the browser's own Web Crypto: PBKDF2-SHA-256 with a random salt and 600,000
iterations turns the password into a non-extractable AES-256-GCM key, and each
save is gzipped (where the browser can) and encrypted under a fresh random IV;
a wrong password or any tampering fails GCM's check. The password is never
stored and the key lives only in the open tab.

Everything about the user's money goes in the vault: the statements
(spreadsheets and OFX/QIF files as their text, a PDF as the transactions read
from it, never the file), their category changes and the column layouts they
fixed. Only display choices stay readable; the sample data is never kept, and
without a password nothing about their money is kept at all. A forgotten
password can't be recovered, only *started over*. The menu can stop keeping
(which deletes the locked copy), change the password, or clear everything. If
storage fills up, the biggest statements are left out and the user is told
which. Open tabs follow each other's saves rather than overwrite them, and a
tab whose password was changed elsewhere locks itself. Data an earlier version
kept readable is loaded once, and the user is asked to lock it or remove it.

#### Reading statements

`formats.js` turns a file into `{ date, amount, desc, memo, bankCat, account }`,
with `amount` signed from the account holder's side (negative is money out).

- **CSV / TSV**, any delimiter, any column order, with or without a header row,
  with or without a preamble above it. Columns are matched by name (English
  and the common European bank headings) and then checked against what they
  actually hold; anything still missing is found from the values alone.
- **Dates**: year-first, day-first, month-first, month names, compact `20250304`,
  Quicken's `3/4'25`. Day-first vs month-first is settled by any value above 12,
  then by which reading keeps the rows in date order, then by hints such as
  decimal commas or a pound/euro currency.
- **Amounts**: currency signs and codes, `1.234,56`, `(12.50)`, `12.50-`, `CR`/`DR`.
- **Signs**: separate debit/credit columns; a type column for unsigned amounts;
  otherwise the descriptions ("PAYMENT THANK YOU" is money in), the running
  balance and the plain majority vote on whether purchases are negative or
  positive (credit card exports often make them positive).
- **OFX / QFX** (SGML and XML) and **QIF**.
- Text is decoded as UTF-8, UTF-16 when a byte-order mark says so, and
  Windows-1252 otherwise.

When a spreadsheet leaves real doubt (an unsettled date order, guessed signs,
a missing column) the user gets a short review dialog with a live preview and a
count of money in and out. A layout fixed there is remembered by its header
row, so that bank's next export goes straight in.

#### PDF statements

A PDF is laid out for printing, so `pdfstatement.js` reads it from where the
words sit rather than from any one bank's format. pdf.js supplies each page's
text with positions; `parse()` (pure, so it is tested in Node) does the rest:

- **Lines and cells**: text is grouped into lines by height and into cells by
  the gaps between words. Whole lines printed as one run padded with spaces
  (typewriter-style statements) are cut at the padding, and an amount crowded
  by a long description is still split off.
- **Column headings** are found by their words ("Trans Date", "Withdrawals/
  Subtractions", "Money in (£)", "Balance"...), including headings stacked over
  two or three lines and tables printed two or three times side by side. A
  row's date must sit in a date column, and its amounts are placed by column.
- **Sections** ("Payments", "Other Credits", "Checks Paid", "Purchases, Balance
  Transfers & Other Charges"...) give the direction when the columns don't;
  summaries, daily balances, interest calculations, year-to-date totals and
  notices are skipped. "(continued)" titles carry a section, and its printed
  total, across a page break.
- **Signs**: in/out columns, `CR`/`DR`, printed minus signs (which mean opposite
  things on a card and a bank statement), sections, type columns, and a
  running balance, which settles any direction that was only a guess.
- **Dates and years**: day-first or month-first comes from the statement
  period if only one reading makes sense, then from the row dates; rows
  printed without a year take it from the statement period, so a January
  statement's December rows land in the year before.
- **Noise**: running heads and feet repeated on every page are ignored, a row
  needs words as well as a date and an amount, rows dated outside the
  statement period (a payment due date, an offer's end date) are dropped, and
  a row with no column headings or section to vouch for it must line up with
  other rows. Undated interest and fee lines take the closing date.
- **Checks**: every "Total ..." line the statement prints and its opening and
  closing balances are compared with what was read. A statement that adds up
  goes straight in; one that doesn't, or whose signs had to be guessed, gets
  the review dialog with the checks listed, a live preview and a switch to
  swap money in and out. Locked PDFs ask for their password; scans (no text)
  and non-statements are reported rather than half-read.

Re-importing overlapping statements adds only what is new: a transaction's id
is its date, amount and description plus how many times that trio already
appeared in its file, so two identical coffees on one day both survive.

#### Categories

`categories.js` holds 21 categories, each an expense, income or transfer.
Transfers (between your own accounts, card payments, Venmo/Zelle and the like)
count as neither spending nor income, and refunds net down the category they
came from. First match wins:

1. a transaction the user re-filed by hand,
2. a rule the user made for its merchant ("file every Blue Bottle under Dining"),
3. a known merchant or unmistakable phrase (a few hundred of them),
4. the bank's own category column, when the export has one,
5. generic words ("restaurant", "pharmacy"),
6. otherwise money in is Income and money out is Uncategorized.

Merchant names are cleaned for display and grouping: card-processor prefixes,
store numbers, references, dates and padded locations are stripped, so
`POS PURCHASE SQ *BLUE BOTTLE COFFEE 0432  OAKLAND CA` becomes *Blue Bottle
Coffee*.

#### Charts

`charts.js` is a small hand-written SVG library: no dependencies, animated with
`requestAnimationFrame`, and still when the user prefers reduced motion. Every
chart has a hover/focus tooltip that lists every series with the value first;
the period charts and the calendar can be read with the arrow keys; the two
period charts have a table view, and the category breakdown is itself a table.

The eight category colours are a validated categorical palette, checked with an
OKLab colour-vision simulation and for contrast against the dark card surface
(`#1b1240`) the charts sit on. The top eight categories by all-time spend hold
them; the rest fold into a grey *Everything else*. Colours follow the category,
not its rank in the current view, and keep their slot when the user re-files
things, so nothing repaints under them. The calendar uses a single-hue pink
ramp split at spending quantiles, so one rent day does not wash out the month.

Filters narrow in this order: account → date range (presets or the brush over
the whole history) → a focused category (every chart) → an opened period (the
details below the divider) → a day, merchant or search (the transaction list).

`window.Spendscape` exposes `state()`, `txns()`, `loadSample()`,
`importText(name, text)`, `setPreset()`, `setGran()`, `setMode()`, `setFocus()`
and `togglePeriod(isoDate)` for driving the app from a test harness.

### 还泪记

A visual novel of *Dream of the Red Chamber* (红楼梦), in Chinese. You are
林黛玉, the crimson pearl grass (绛珠草) come down to the world to repay the
stone's daily watering with every tear of a lifetime. Eight chapters drawn
from the novel's best-known episodes (初见, 西厢, 葬花, 知己, 诗社, 秋窗, 冷月,
还泪), each titled with the novel's own chapter couplets, plus a prologue, a
snow epilogue and four endings. A playthrough is about 330 lines.

#### The tears

Her tears are ten crimson pearls on a red string. A tear shed for 宝玉 drops
into the jade (宝玉) and is *repaid*; a tear for anything else (homesickness,
a quarrel, an opera, the rain) falls *in vain*. There are four chances to weep
for him and eight to weep for anything else before the winter, so weeping at
every turn spends the string by the mid-autumn moon and ends the story there
(冷月葬花魂). In the last chapter whatever is left falls at once: repaid if she
lets him go gently, in vain if she burns her poems. The true ending
(质本洁来还洁去) needs her not to have burned them, to say 「你放心」 at the end
(which takes enough closeness, or having said it in 知己), and six pearls
repaid, which works out to no more than four tears in vain before winter.
Closeness (`heart`) and her friendship with 宝钗 (`orchid`) are kept but never
shown.

#### How it looks

- **A paper diorama.** Every scene is four to six flat layers cut from paper
  at different depths, with drop shadows between them, a soft-light rice
  paper grain over everything and slow parallax. Far layers are ink wash,
  near ones are cut sharp. Light (lanterns, candles, the moon) is a separate
  layer screened over the night tint. Changing scene is a pop-up book turning
  its page: the old cut-outs fold flat front first, the new ones stand up from
  the back; the dream uses a spreading ink blot instead.
- **Painted in code.** `scenery.js` and `buildings.js` generate skies, ink
  ridges, gilded 祥云, trees with moss dots, bamboo in 个 and 介 leaf clusters,
  banana leaves, withered lotus, Taihu rocks, walls under grey tiles with moon
  gates, cracked-ice lattices (a square cut again and again by straight lines),
  roofs, gatehouses, lanterns, screens, desks, candles, braziers, bed curtains.
  Everything is seeded, so a scene is the same on every visit.
- **The cast** are paper-cut profiles assembled from parts (`figures.js`):
  one face with open, lowered or closed eyes; eight hairstyles; garments,
  vests, motifs, pendants, wraps and props; six arm poses with their sleeves.
  `cast.js` dresses them as the novel describes where it does (宝玉's purple-gold
  crown, 宝钗's honey, rose-purple and onion-yellow with her golden locket,
  凤姐's phoenix pin, 黛玉's crimson cloak lined with white fox). Figures fold up
  from the page when they enter; the speaker steps forward and the others dim.
- **A manuscript page.** The text is set vertically, right to left, on paper
  ruled in red (朱丝栏), each character inking in. Speakers are red seals. Red
  marginal notes (朱批) appear beside some lines in a running hand: those
  marked with a source (甲戌本脂批, 庚辰本脂批) are real 脂砚斋 commentary, the
  rest belong to this edition. There is a horizontal layout in the settings.
- **Choices are flower lots** (花签) drawn from a bamboo pot. **Poems** unroll
  on a hand scroll; famous poems appear as short excerpts. In the poetry club
  you build your own 咏白海棠 couplet by couplet; every option keeps the same
  tonal pattern and rhymes (门 盆 魂 痕 昏), so any mix is a regular 七律, and
  the judge reacts to whose style it leans toward.

#### Sound

`audio.js` makes everything with Web Audio: a plucked string (Karplus-Strong)
improvising phrases on the pentatonic modes (宫商角徵羽), one mood per scene,
with octaves, bends and the occasional glissando, through a reverb made from
decaying noise; rain and wind from filtered noise; and the small sounds (a
pearl into jade, lots drawn, a scroll, a seal) from a few oscillators each.
It starts on the first click or key.

#### The script

`story.js` holds the whole story as text in the format `engine.js` reads:

```
## ch2 | 第二折 · 西厢 | 西厢记妙词通戏语　牡丹亭艳曲警芳心
@bg qinfang day                  stage commands: bg show pose hide fx music
@show baoyu book r               sound tear set if goto poem note card ...
宝玉：好，好，来把这个花扫起来。      a line; the speaker must be a known name
（只是这一身的眼泪……）               黛玉's unspoken thought
? 落花该往哪里去？                   a choice, then its options:
* [heart>=3] 「……」 -> c2_bury | heart+1
```

The parser checks that every jump lands on a label and every poem, ending
and composition exists. Simulating the story with random choices reaches all
four endings.

#### Fonts

LXGW WenKai (正文), Ma Shan Zheng (titles, seals, name boards) and Zhi Mang
Xing (the red notes), all SIL OFL 1.1, cut down to the characters the game
uses: about 620 KB together instead of 35 MB. After changing any text, run
`python3 apps/honglou/fonts/build.py <dir with the source TTFs>` (needs
`fonttools` and `brotli`).

#### Saving

`localStorage` entry `tutu.honglou.v1`: settings, the chapters, poems and
endings unlocked, which lines have been read (so 快进 skips only those), nine
save pages, a quick save and the place 续读 resumes from. Chapters can be
replayed from 回目 with the pearls as they were.

`window.Honglou` exposes `state()`, `start(label, vars)`, `advance()`,
`choose(i)`, `settle()` and `program` for driving the game from a test
harness.

## Deployment

GitHub Pages is configured under **Settings → Pages** as
**Source: Deploy from a branch**, branch `master`, folder **/ (root)**.

Pushing to `master` is the whole deploy. GitHub runs its own *pages build and
deployment* job; there is no workflow in this repo and nothing to maintain.

Two things this setup depends on:

- **`.nojekyll` must stay at the repo root.** Branch-based Pages runs the files
  through Jekyll by default, which skips paths beginning with `_` and can
  rewrite others. This file turns that off and serves the tree verbatim.
- **Paths stay relative.** The site is served from `/tutu/`, not a domain root,
  so absolute paths like `/assets/…` would break. Use `assets/…` from the hub
  and `../../assets/…` from an app.
